Contexto

En banca, un fallo en una transferencia nunca es un detalle. En NTT DATA automaticé pruebas para el sector bancario, primero en prácticas y luego como QA Tester junior. El framework es un proyecto de equipo con fin didáctico: un banco simulado para aprender a probar APIs.

Qué hice

  • Diseñé y ejecuté pruebas automatizadas para banca con Selenium, JUnit y Cucumber, con los estándares de calidad del sector financiero.
  • Con el equipo del framework construimos la API REST en Java y Spring Boot: clientes, cuentas, tarjetas y transferencias sobre H2 en memoria.
  • La protegimos con JWT: el login deja el token en una cookie y un filtro responde 401 a toda petición sin sesión, salvo las rutas /public.
  • Escribimos las pruebas en Gherkin con Cucumber y JUnit 5, con los pasos agrupados por controlador y un contexto compartido.

Arquitectura

Un proyecto Maven con dos mitades: el banco y el framework que lo recorre como un cliente. La suite arranca Spring Boot y habla con la API por HTTP a través de BankAPI, una interfaz Java con todos los endpoints.

  1. Un escenario en Gherkin describe el caso con ejemplos: registrarse con N cuentas y M tarjetas, entrar y consultar las tarjetas.
  2. Cada paso vive en el fichero de su controlador y deja sus datos en el TestContext para el siguiente.
  3. BankAPI lanza la petición por HTTP con la cookie del login.
  4. La API valida el JWT y baja por controlador, servicio y repositorio hasta H2; el paso comprueba la respuesta.
  5. Al acabar cada escenario, un @After borra lo que creó y vacía el contexto.
  6. En cada push a main, GitHub Actions ejecuta la suite y sube al repositorio el informe de Cucumber en HTML y PDF.

Qué aprendí

Que una prueba vale lo que se entiende al leerla. Gherkin obliga a nombrar cada paso como lo diría negocio, y repartir los pasos en ficheros me enseñó que el estado compartido de una suite se diseña desde el principio, no se descubre cuando falla.
